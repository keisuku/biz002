# Phase 2 報告 — 生死判定の前に、まず読むもの

指示書 §9 の「§4.1 に到達したら必ず一度立ち止まり、数字を見てから続行を判断すること」に対する報告。

---

## 1. 結論（先に）

**手法の生死は判定できていない。実データが 1 件も取得できていないため。**

この開発環境の外向き通信は組織の egress ポリシー配下にあり、Binance の配布ホストが
すべて拒否される。プロキシの記録した拒否理由は「gateway answered 403 to CONNECT
(policy denial)」で、`data.binance.vision` / `fapi.binance.com` / `api.binance.com` /
`data-api.binance.vision` のいずれも同じ。回避は行っていない（ポリシー拒否は回避対象ではない）。

したがってこの報告に「BTCUSDT の mfe_60 中位値は〜」という数字は無い。
無いものを推定で埋めることはしない。**必要なのはコードではなくデータである。**

やったこと: Phase 1 と Phase 2 のコードを全部書き、既知の正解を埋め込んだ合成データで
端から端まで動作を確認し、実データが入った瞬間に §4.1 の数字が出る状態にした。

## 2. データ取得について（実行時に確認すべきこと）

指示書には「パス構造とファイル形式は記憶に基づく記述なので、実装前に必ずディレクトリ一覧を
取得して実際の構造を確認せよ」とある。**この確認は実行できていない**（上記のとおり接続不可）。
そのため実装は、確認できないことを前提にした作りにしてある:

* `src/data/download.py` は S3 の ListBucket を叩いて `data/futures/um/daily/` 直下の
  **実在するディレクトリ名を列挙**し、そこからキーを組み立てる。指示書のパスは起点にすぎない。
* 組み立てたキーが実在しなければ、同ディレクトリの実ファイル名から日付で引き当て直し、
  差異を WARNING でログに出す。
* 取得した構造は `reports/data_layout.json` に保存される。**最初に見るべきファイル。**
* 種別名は大小文字・単複のゆれを吸収して解決する（`aggtrades` → 実在する `aggTrades`）。
* CSV はファイルごとにヘッダ有無・列数・時刻粒度（秒 / ms / µs / ns）を判定する。
  Binance は配布途中でこれらを変えており、決め打ちは静かに壊れる原因になる。
* `.CHECKSUM` があれば必ず検証する（ハッシュ長からアルゴリズムを判定）。

通信が通る環境で最初に流すのはこれ:

```bash
python -m src.cli discover --symbol BTCUSDT   # reports/data_layout.json を確認
```

ここで指示書と実物が食い違っていたら、コードは実物に合わせて動く。合わなければ
`LayoutError` で止まり、その時点で利用可能なディレクトリ一覧を例外に載せて報告する。

## 3. パイプラインの動作確認（合成データ）

実データが無い以上、確認できるのは「機械が仕様どおりに動くか」だけである。
そこで、**構造を意図的に埋め込んだ**合成 aggTrades を 3 種類作って端から端まで流した。

> ここから出る数字は手法の期待値ではない。人工データに自分で埋めたものを自分で掘り出しただけである。
> 意味があるのは「埋めたものを、埋めた向きで、埋めていない場所を拾わずに検出できたか」という一点。

| profile | 世界の性質 | 検出 | §4.1 判定 | mfe_60 中位値 / コスト |
|---|---|---|---|---|
| `realistic` | 凪の 8σ 程度の発火 | 21 件 / 12 日 | **FAIL** | 0.037% / 0.126% = **0.29 倍** |
| `strong` | 凪の 50σ + 発火幅 2 倍の継続順行 | 361 件 / 60 日 | **PASS** | 2.158% / 0.513% = **4.21 倍** |
| `null` | 50σ の発火だが継続順行ゼロ（対照群） | 156 件 / 25 日 | **FAIL** | 0.319% / 0.511% = **0.63 倍** |

確認できたこと:

1. **適合率 100%** — 検出した発火はすべて、埋め込んだ発火と ±20 秒以内で一致し、方向も一致した
   （`tests/test_integration_pipeline.py`）。埋めていない場所での誤検出はゼロ。
2. **生死判定が常に PASS を返す壊れ方をしていない** — 継続順行の無い `null` 世界では
   正しく FAIL を返し、その場でパイプラインが停止する。
3. **`strong` でだけ §4.3〜§4.5・§6 のコード経路が動く** — PASS 側の下流処理が
   実際に完走することを確認した（成果物は `reports/SYNTHSTRONG/`）。

### 3.1 コストモデルについて分かったこと（合成データでも意味がある観察）

`strong` を作る過程で、当初は「発火を大きくすれば PASS するだろう」と考えたが**しなかった**。
推定スリッページが発火時の約定間ギャップと 1 秒レンジに比例するため、発火を大きくすると
MFE もコストも同じだけ大きくなり、**比がほぼ不変**になる。

これは合成データの性質ではなく、採用したコストモデルの性質である。含意:

> 「大きく飛んだ発火ほど儲かる」は成立しない。飛んだぶんだけ約定も滑る。
> 期待値を決めるのは**発火の大きさではなく、発火の後にどれだけ続くか**（継続順行 / 発火幅）。

実データでこの比が 3 倍を超えるかどうかが、この手法の生死そのものになる。

### 3.2 §4.2〜§4.5 の出力（`strong` 世界、参考）

* 保有時間: H=60s が最良（合成側で継続順行を 45 秒に設定したことの反映であって、発見ではない）
* 出口ルール: E1〜E5 のいずれも E4（固定時間）に**有意に勝てない**（対応のある t 検定、全て p<0.05 で負け）。
  この世界では順行が時間で素直に伸びるため、フロー減衰で早く降りると取り逃す。実データでの結論は当然別。
* コスト感度: 1.5 倍 / 2 倍でも正（この世界では発火幅が極端なので当然）
* §4.5 ストップ滑り: tick 実測でストップ約定価格を推定し、意図した損失幅との差を集計（`stop_slippage.csv`）
* §6: 972 通りの格子を全探索、試行回数 973 をログに記録、ウォークフォワード 9 分割で
  OOS 8/8 fold 正、プラトー判定通過（近傍 100%）、素の Sharpe 5.01 に対し
  試行回数で割り引いた **DSR 0.9989**（SR0 = 3.29）、ブロックブートストラップ 95% CI [1.82, 1.93]

## 4. 実データが入ったときの手順

```bash
python -m src.cli discover    --symbol BTCUSDT
python -m src.cli download    --symbol BTCUSDT --start 2023-08-01 --end 2026-07-29
python -m src.cli bars        --symbol BTCUSDT --start 2023-08-01 --end 2026-07-29
python -m src.cli verify-flags --symbol BTCUSDT --start 2023-08-01 --end 2026-07-29
python -m src.cli refs        --symbol BTCUSDT --start 2023-08-01 --end 2026-07-29
python -m src.cli events      --symbol BTCUSDT --start 2023-08-01 --end 2026-07-29
python -m src.cli analyze     --symbol BTCUSDT --tick-stops
```

`analyze` の最初の出力が §4.1 の判定である。**そこで一度止まる。**
FAIL なら時間帯分析にも出口シミュレーションにも進まない（進むには `--force` が要る）。

見るべき数字は 1 つ:

```
mfe_60 の中位値 > 3 × (往復手数料 0.10% + 推定スリッページ×2)
```

ETHUSDT でも同じ手順を回し、BTC/ETH の両方を見てから次を判断する。
通過した場合のみ `validate`（§6）へ進み、通過しなければ**パラメータを探しに行く前に報告する**。

### 事前に決めておくべきこと（数字を見る前に）

指示書 §9 のとおり、「性能が出ないので調整しました」を試行回数に加算する仕組みは用意した
（`python -m src.cli trials --n <回数> --note "..."`）。DSR はこの累計を使って割り引く。
閾値をいじった回数を申告し忘れると、DSR の数字は意味を失う。

## 5. 実装で指示書と異なる判断をした点

| 箇所 | 指示 | 実装 | 理由 |
|---|---|---|---|
| 凪の分位点 | 過去 7 日の rv(1800) 分布の下位 25% | 分足サンプルに落としてから分位点を取る | 秒単位 60 万行の rolling 分位点は計算量の無駄。推定量として等価 |
| 参照統計 | 「直近 1 時間の標準偏差」 | 窓を k 秒（発火の窓幅）だけ過去にずらす | ずらさないと発火が自分の基準値を押し上げ、閾値が過小評価される |
| MAE | 「最大逆行幅」 | 一度も逆行しなければ 0（MFE も同様に 0 下限） | 定義どおり。逆行していないのに正の「逆行幅」が出ると集計が壊れる |
| 探索の評価軸 | 明示なし | 固定時間決済（既定 60 秒）の純リターンで統一 | 出口ルールと閾値を同時に探索すると試行回数が爆発する。出口は §4.4 で別に扱う |
| スリッページ | 「発火時のスプレッドと価格インパクトから推定」 | 半スプレッド + 約定間ギャップ + 発火秒レンジの加重和。往復で 2 回払う | bookTicker が無い期間でも同じ式が使えるようにするため（§2.3 の非対称性対策） |

いずれも `config/params.yaml` で調整できる。ハードコードした定数は無い。
